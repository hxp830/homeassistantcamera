# Gesture YOLO HA (Русский)

Gesture YOLO HA — система распознавания жестов с нескольких видеопотоков для Home Assistant.
Поддерживаются модели YOLO `.pt`, встроенный движок MediaPipe, MQTT Discovery и многоязычная веб-консоль.

## 1. Возможности

- Несколько источников видео (USB-камера / RTSP)
- Поддержка моделей:
  - Файлы YOLO `.pt` (можно загружать)
  - Встроенная `mediapipe_hands`
- Переключение моделей:
  - Глобальная модель
  - Отдельная модель для каждой карточки
- Веб-интерфейс:
  - Матрица мониторинга со статусом подключения и частотой кадров
  - Клонирование карточки
  - Копирование MQTT-топика
  - Переключение языка (китайский / английский / русский)
- Интеграция с Home Assistant через MQTT Discovery, а также MJPEG-поток,
  который можно использовать как сущность камеры `mjpeg`
- Камеры и настройки MQTT сохраняются между перезапусками

## 2. Требования

- Python 3.10+ (рекомендуется 3.11)
- Доступные видеопотоки
- MQTT-брокер + интеграция MQTT в Home Assistant (для связки с HA)

## 3. Быстрый старт

### Windows PowerShell

```powershell
cd gesture-yolo-ha
.\run.ps1
```

`run.ps1` создаёт виртуальное окружение, устанавливает зависимости только при
изменении `requirements.txt`, создаёт `.env` и запускает сервис.

### Linux / macOS

```bash
cd gesture-yolo-ha
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Откройте: `http://127.0.0.1:8000/`

## 4. Безопасность

Загрузка модели `.pt` **выполняет код из файла**. Любой, кто имеет доступ к порту
сервиса, может загрузить и активировать модель и выполнить произвольный код на
вашем хосте.

- Задайте `API_TOKEN` в `.env`, чтобы требовать токен для всех запросов `/api`,
  `/snapshot` и `/stream`.
- Токен принимается через заголовок `Authorization: Bearer <token>`, заголовок
  `X-API-Token`, параметр `?token=` или cookie, полученную из `POST /api/login`.
- Если `API_TOKEN` пуст, API открыт — так можно делать только в полностью
  доверенной локальной сети. При старте выводится предупреждение.
- `GET /api/mqtt` возвращает `********` вместо реального пароля брокера.
- Никогда не храните реальные учётные данные в `.env.example`. Файл `.env`
  добавлен в `.gitignore`.

## 5. Конфигурация (.env)

### Основное

- `HOST`, `PORT`
- `API_TOKEN` — пусто отключает аутентификацию
- `MAX_UPLOAD_MB` — лимит размера загружаемой модели, по умолчанию 200

### Распознавание

- `MODEL_DIR`, `MODEL_FILE` (имя `.pt` или `mediapipe_hands`)
- `SOURCE` (`0`, `rtsp://...` или `auto`)
- `CONF`, `IOU`, `IMG_SIZE`, `DETECT_INTERVAL`
- `SHARE_MODELS` — использовать одну загруженную копию `.pt` для всех камер
  (по умолчанию `true`, заметно снижает расход памяти)

При `SOURCE=auto` URL RTSP собирается из `RTSP_HOST`, `RTSP_PORT`, `RTSP_USER`,
`RTSP_PASSWORD` и `RTSP_PATH`.

### Производительность предпросмотра

- `JPEG_QUALITY` — качество JPEG предпросмотра, по умолчанию 80
- `PREVIEW_WIDTH` — ширина масштабирования, `0` сохраняет исходное разрешение
- `PREVIEW_FPS` — ограничение частоты кодирования предпросмотра, по умолчанию 15.
  **Ограничивается только частота создания JPEG; распознавание всегда работает на
  полной частоте потока.** Снижайте это значение при нескольких камерах на слабом
  оборудовании
- `IDLE_ENCODE_TIMEOUT` — прекратить кодирование кадров, если никто не смотрит
  дольше указанного числа секунд (на распознавание не влияет), по умолчанию 15

### MQTT

- `MQTT_HOST`, `MQTT_PORT`, `MQTT_USER`, `MQTT_PASSWORD`
- `MQTT_CLIENT_ID`, `MQTT_DISCOVERY_PREFIX`, `MQTT_STATE_TOPIC`
- `MQTT_KEEPALIVE` — по умолчанию 60
- `MQTT_PUBLISH_MODE` — `change` публикует только при смене жеста (по умолчанию),
  `always` публикует каждое распознавание
- `MQTT_HEARTBEAT` — повторная публикация текущего жеста не реже чем раз в N
  секунд, `0` отключает

## 6. Веб-консоль

- Добавление и удаление карточек источников
- Загрузка и переключение моделей
- Отдельный выбор модели для каждой карточки
- Клонирование карточки из существующего источника
- Переключатель языка в правом верхнем углу
- Индикатор подключения и частота кадров на каждой карточке; клик по
  изображению открывает полноэкранный MJPEG-просмотр

Примечания:

- Интерфейс защищает несохранённые правки: обновление по таймеру не затирает то,
  что вы вводите или выбираете.
- Tailwind поставляется локально в `app/static/vendor/`, поэтому консоль
  работает в изолированной сети без доступа в интернет.

## 7. Интеграция с Home Assistant

MQTT Discovery публикуется при старте и при каждом переподключении, включая
топик доступности, чтобы сущности отображались как недоступные при остановке
сервиса.

Полезная нагрузка состояния содержит:

- `gesture`
- `confidence`
- `model`
- `timestamp`
- `source_id`

### Сущность камеры

`/stream/{source_id}.mjpg` — стандартный MJPEG-поток:

```yaml
camera:
  - platform: mjpeg
    name: Жесты в гостиной
    mjpeg_url: http://<ip-сервера>:8000/stream/cam1.mjpg
```

Добавьте `?token=<ваш-токен>`, если включён `API_TOKEN`.

## 11. Диагностика задержки предпросмотра

Отставание RTSP-картинки от реальности — самая частая жалоба. Задержка может
возникать в трёх местах: камера, этот сервис, браузер. Ниже описано, что сервис уже
делает, а затем — как найти остальное.

### 11.1 Что уже сделано в сервисе

**Захват отделён от кодирования.** На каждый источник работают три потока: поток
захвата только вызывает `cap.read()`, передаёт кадр потокам распознавания и
предпросмотра и сразу возвращается к чтению. Отрисовка наложения и кодирование JPEG
никогда не выполняются в потоке захвата. Это важно: если поток захвата не успевает за
частотой потока, кадры накапливаются в очереди декодера FFmpeg, и это выглядит как
постоянная задержка около секунды.

**Кадры отбрасываются, а не выстраиваются в очередь.** Если кодировщик предпросмотра
не закончил предыдущий кадр, новый заменяет его. Поэтому кодирование не может
замедлить захват, а задержка не накапливается со временем.

**Входная буферизация FFmpeg отключена.** Параметры захвата по умолчанию:

```
rtsp_transport;tcp|fflags;nobuffer|flags;low_delay|reorder_queue_size;0|max_delay;0|stimeout;5000000
```

Всю строку можно переопределить через `OPENCV_FFMPEG_CAPTURE_OPTIONS` в `.env`. В
локальной сети UDP может дать ещё немного меньшую задержку ценой артефактов при
потере пакетов:

```bash
OPENCV_FFMPEG_CAPTURE_OPTIONS=rtsp_transport;udp|fflags;nobuffer|flags;low_delay|max_delay;0
```

### 11.2 Поиск источника задержки с помощью пробника

`tools/latency_probe.py` декодирует поток с теми же параметрами FFmpeg, что и сервис,
но без распознавания, без кодирования JPEG, без HTTP и без браузера. Оставшаяся
задержка принадлежит камере, сети или декодеру.

```bash
python tools/latency_probe.py                     # первый RTSP-источник из data/sources.json
python tools/latency_probe.py 102                 # источник, в URL которого есть "102"
python tools/latency_probe.py rtsp://... --headless --seconds 12
```

Без `--headless` открывается окно предпросмотра с часами в углу. **Направьте камеру
на это окно на мониторе**: в видео появится изображение тех же часов, и разница между
ними и живыми часами и есть реальная сквозная задержка. Выход — клавиша `q`.

Главный показатель — `read avg`:

- **`read avg` большой (десятки миллисекунд)** — каждый кадр уходит на ожидание
  камеры, узкое место в камере или сети, смотрите 11.3
- **`read avg` близок к нулю** — кадры уже стояли в очереди, узкое место на нашей
  стороне; снизьте `PREVIEW_FPS`, `PREVIEW_WIDTH` или `JPEG_QUALITY`
- **`display avg` большой** — медленно отрисовывается только окно предпросмотра,
  добавьте `--headless`, чтобы исключить этот фактор

Особенно показательно сравнить основной и дополнительный потоки с `--headless`: если
1280x720 и 352x288 дают одинаковую частоту кадров, узким местом не может быть
декодирование, ведь большой кадр декодируется более чем в десять раз дороже.

### 11.3 Что проверить на камере

Настройки самой камеры обычно дают большую часть задержки. Для камер Hikvision в
веб-интерфейсе проверьте:

- **Время экспозиции / медленный затвор** (Конфигурация - Изображение - Настройки
  отображения). **Это самая незаметная и самая влиятельная настройка.** При нехватке
  света камера удлиняет экспозицию, чтобы осветлить картинку, и частота кадров падает
  вдвое. Экспозиция 1/12 с означает 12 fps, 83 мс собственной задержки на кадр и смаз
  движения. Установите 1/50 с или быстрее; если картинка темнеет, сцене нужен свет
- **Интервал I-кадров** — установите в одну-две частоты кадров (25 или меньше при
  25 fps). Чем чаще ключевые кадры, тем быстрее старт декодера и переподключение
- **Сглаживание потока** — сдвиньте полностью в сторону «чёткости». Сглаживание
  выравнивает битрейт за счёт буферизации, а этот буфер и есть задержка
- **Кодек** — предпочтительно H.264; H.265 декодируется на CPU значительно медленнее
- **Сложность кодирования** — установите «низкую». Высокая добавляет межкадровый
  анализ и, соответственно, задержку
- **Тип потока** — убедитесь, что правите именно тот поток, который забираете.
  `/Streaming/Channels/101` — основной поток, `/102` — дополнительный; правка не того
  потока ничего не изменит

Обратите внимание и на разрешение. При типичном для дополнительного потока 352x288
(CIF) MediaPipe плохо различает суставы пальцев, и распознавание становится
нестабильным. Если качество распознавания низкое, поднимите дополнительный поток выше
640x480 или переключите этот источник на основной поток.

### 11.4 Перекрёстная проверка через VLC

VLC **по умолчанию буферизует 1000 мс сетевого кэша**, поэтому при прямом открытии
RTSP видна задержка около секунды, что ведёт к неверному выводу. Обязательно
отключайте кэш:

```bash
vlc --network-caching=0 --rtsp-tcp "rtsp://user:pass@host:554/Streaming/Channels/102"
```

То же касается фирменного клиента Hikvision iVMS-4200: в разделе «Конфигурация
системы - Просмотр - Производительность воспроизведения» выберите минимальную
задержку, иначе измерение не имеет смысла.
